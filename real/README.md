# lib_copilot

도서관에서 새 책에 **청구기호(852 ▼h)** 를 매기는 일을 돕는 사서-AI 협업 에이전트.

**쉬운 책은 자동으로 끝내고, 판단이 갈리는 책만 사람에게 넘긴다.**

---

## 왜 만드나

새 책이 들어오면 사서가 청구기호를 매긴다. 이 번호가 곧 책이 꽂힐 자리다.

이 일에는 성격이 다른 두 문제가 섞여 있다.

**① 반복적이다.** 매 권마다 같은 검색을 손으로 되풀이한다 — 업체 번호를 본교에서 확인하고, 타대학 분포를 보고, 다시 본교로 돌아와 맞춰본다. → **자동화한다.**

**② 일관되지 않다.** 판단이 사서의 암묵지에 기대 있어 사람마다 갈린다. 실제로 사서가 처리한 12권 중 **4권이 작성자가 매긴 번호를 교열 담당자가 뒤집었다**:

| 책 | 작성자 | 교열 최종 |
|---|---|---|
| 사랑받는 서점을 만들기 위해 2000일 | 658.827 (소매경영) | **381.45002** (서적판매업) |
| 어느 완벽한 이중언어자 | 400.42 (언어학) | **306.446** (사회학) |
| 부린 왕자 | 179.9 (자기계발) | **332.6324** (부동산투자) |
| 일리아스 좋아하세요? | 883 (그리스문학) | **028.9** (독서) |

둘 다 틀리지 않았다. 같은 책을 어느 관점에서 보느냐의 문제다. → **판단이 갈리는 지점에만 사람이 개입한다.**

그래서 이 도구는 "정답을 맞히는 기계"를 목표로 하지 않는다. **확실한 건 답 하나로 끝내고(①), 갈리는 건 후보와 근거를 함께 내놓고 사서에게 넘긴다(②).**

---

## 어떻게 도는가

> **독립 shelf_fit + 3단계 전환은 완료됐다.** 현재 배선의 상세는
> `docs/design.md`와 `docs/system_flow_draft.md`에 있다.

사서가 실제로 하는 순서를 그대로 옮겼다. **LLM 호출은 두 종류뿐이다** —
LLM-F(독립 shelf_fit: 책 1권 × 서가 1곳)와 LLM-K(키워드 추출). 나머지는 전부 코드다.

```
① 책 입력                  제목 · 저자 · 082(업체번호) · 원제(있으면)
   ▼
② 알라딘 보강              비어 있는 칸만 채운다 — 책소개 · 원제 · 부제
   │                       조어 제목은 이게 없으면 못 푼다
   │                       (「부린 왕자」는 제목 어디에도 '부동산'이 없다)
   ▼
③ 원제로 승계 검색         본교서지에서 원표제가 그 원제로 시작하는 책   ← 정렬표 · 3ms
   ├─ 찾음  ──────────────▶ 그 번호 승계. 끝.  LLM 안 부름     예: 「바빌론 부자들의 지혜」
   ▼
④ 제목으로 승계 검색       제목이 입력 제목으로 시작 + 뒤가 문장부호/끝  ← 정렬표 · 5ms
   ├─ 찾음  ──────────────▶ 그 번호 승계. 끝.  LLM 안 부름
   └─ 못 찾음  ───────────▶ 1단계로                            12권 중 11권이 여기로

【1단계】 082
   LLM-F ×1               082 **서가** 40권만 보여준다. "이 서가에 꽂혀도 어울리나?"
   │                       (082 번호 자체는 LLM에 안 준다 — 책 내용이 아니라 코드의 prior다)
   │                       ⚠️ 082가 없거나 그 번호대 본교 책이 0권이면 건너뜀
   │                       게이트 없음 — 082는 후보 하나일 뿐이다
   ▼
【2단계】 + 종합서지
   검색(코드)              타대학 득표 3위까지 · 082와 같은 번호 제외 · 본교 0권 제외
   LLM-F ×N               **새로 생긴 후보에만** 1회씩 — 082 점수는 1단계 것을 그대로 쓴다
   ├─ 게이트              여기까지로 이미 수렴이면(점수·격차 둘 다 통과) 끝. 키워드를 안 돈다
   │                      12건 중 #3·#4·#6이 여기서 정답으로 종결
   ▼
【3단계】 + 키워드
   LLM-K ×1               **책 정보만** 넣는다(약 1,000토큰) → 검색어 3~5개 (한국어+영어 LCSH)
   │                       ⚠️ 서가를 안 보여준다 — 보여주면 그 어휘로 물든다
   검색(코드)              제목·650에 2개 이상 걸린 책만 → 청구기호로 묶어 상위 후보
   │                       기존 번호가 또 걸리면 후보를 새로 안 만들고 출처 라벨만 추가
   LLM-F ×N               역시 새 후보에만 · 서가는 다른 후보와 같은 40권
   ▼
판정 (LLM 0회)            decide.decide() — 점수 내림차순 정렬 후 수렴 판정(converged).
                          수렴이면 ✅ 1순위가 정해졌습니다, 아니면 ⚠️ 사서가 가른다.
                          **확정은 어느 쪽이든 사서가 버튼으로 한다** — 수렴이면 클릭 한 번.
```

**왜 후보마다 따로 매기나** — 예전엔 후보 5~8개를 한 프롬프트에 넣고 한꺼번에 점수를
매겼다. 같은 책·같은 번호라도 옆에 누가 들어왔느냐로 점수가 달라져서, 문턱이 회차마다
다른 뜻을 갖게 되고 재산정이 불가능했다. 지금은 점수가 `(책, 서가)` 하나의 함수다.
같은 서가는 전 과정에서 **딱 한 번** 평가된다(082가 세 번 들어가던 중복 제거).

**한 단계 안의 fit 호출은 동시에 나간다**(서로를 안 보므로 결과가 달라지지 않는다 —
config.FIT_CONCURRENCY). 단계 사이는 순차다.

**⑧에서 왜 "2개 이상"인가** — 1개만 걸려도 통과시키면 흔한 낱말이 큰 서가를 통째로
끌어온다. 「게임으로 철학하기」에서 '철학' 하나가 1435권짜리 서가를 데려와 6권짜리 정답을
파묻었다. 2개로 조이면 「어느 완벽한 이중언어자」에서 경합했던 두 번호(306.446·400.42)가
나란히 올라온다. **2개로 고정한다** — 후보가 모자랄 때 1개로 완화하던 폴백은 2026-09-02에
없앴다. 케이스마다 다른 눈금으로 뽑힌 후보가 한 분포에 섞이고, 12건 실측에서 그 폴백이
데려온 건 오답뿐이었다(#7의 100·193 같은 대분류 통째). 0개면 0개인 채로 다음으로 간다.

자세한 배경과 설계 판단은 **[docs/design.md](docs/design.md)** 에 있다.

## 알아야 할 값

흐름을 정하는 건 **LLM이 매기는 점수 하나**와 **코드가 자르는 선 둘**입니다.

### `shelf_fit` — LLM이 매기는 점수 (0.0 ~ 1.0)

"이 신규 도서가 **본교 그 번호대 서가에 꽂혀도 어울리나**"입니다. 후보 번호마다 하나씩 붙습니다.

```
1.0  그 서가 책들과 사실상 같은 성격이다
0.7  주제는 맞는데 성격(전문서/교양서, 이론/실용)이 조금 다르다
0.4  큰 갈래는 겹치지만 초점이 다르다
0.0  전혀 다른 자리다
```

⚠️ **계산값이 아닙니다.** 임베딩 유사도 같은 수식이 없어요. 후보 번호대의 본교 책
40권(제목 + 주제명·요약 등)을 LLM이 읽고 판단해 뱉는 숫자입니다. **그래서 실행마다 흔들립니다.**

⚠️ **확신도가 아닙니다.** "이 답이 맞을 확률"이 아니라 "이 자리에 어울리나"입니다.

현재 운영 프롬프트는 비교실험에서 선택한 **two-axis** 방식입니다. 먼저
`주제·관점 적합도`와 `자료 성격·용도 적합도`를 각각 매기고, 두 값의 산술평균을
`shelf_fit`으로 냅니다. 구체 지시는 `prompts/systemprompt_shelf_fit.txt`, 출력 계약은
`src/schema.py::ShelfFitAssessment`가 담당합니다.

### `THRESHOLD_2` · `GAP_MIN` — 자르는 선 두 개

```
THRESHOLD_2 = 0.80   1순위 점수가 이 값 미만 → 사서
GAP_MIN     = 0.15   1·2위 격차가 이 값 미만 → 사서
```

**두 조건을 다 넘어야 「수렴」이다.** 각자 다른 실패를 막는다:

- **점수**는 *어떤 서가도 확신 못 하는 책*을 막는다. #11 부린왕자는 격차가 0.16까지
  벌어진 회차가 있었지만 1위 점수가 0.71이라 여기서 걸린다.
- **격차**는 *그럴듯한 1위 뒤에 경합이 숨은 책*을 막는다. #9 서점은 1위가 0.90~0.93인데
  사서 두 사람이 갈렸다 — 점수 문턱만 있었다면 틀린 채 확정됐을 건을 격차 0.05~0.10이
  걸러냈다. **1위 점수 하나로는 "사람도 갈린 건"을 못 잡는다**(갈린 책은 두 서가가 다 높다).

이 두 조건은 **두 곳에서 같은 함수로** 쓰인다(`decide.decide()`). 별도 문턱은 없다.

```
2단계 게이트   082+종합서지까지로 이미 수렴이면 → 키워드를 안 돌고 종결
              LIBCOPILOT_STAGE2_GATE (기본 on) · 평가 회차는 자동으로 끈다
최종 판정      3단계까지 간 뒤 같은 두 조건으로 수렴 여부를 판정 → 화면 문구가 갈린다
```

스위치는 게이트 하나뿐이다(끄면 실험용으로 전 건이 3단계까지 간다). 확정은 수렴이든
아니든 **사서가 버튼으로** 한다 — 수렴은 클릭 한 번, 갈림은 골라야 확정된다.
(구 AUTO_CONFIRM 스위치는 "사서 없이 확정"할 경로가 앱에 없어 2026-09-02 제거했다.)

값 근거는 2026-08-25 회차(two_axis, 12건×3회)를 다시 읽어 정했다 — 여유는 격차 쪽
0.31(통과 최소) 대 0.10(저지 최대), 점수 쪽 0.86 대 0.82다.
⚠️ **같은 12건에 되적용한 in-sample 값이라 잠정이다.** 기준선 회차에서 재확인한다.

> 1단계 게이트(`THRESHOLD_1`)는 2026-09-02에 없앴다. 값이 틀린 게 아니라 **존재하지
> 않는다** — 082가 정답인 유일한 케이스(#8, 0.70~0.80)보다 082가 오답인 #7(0.85~0.90)과
> 사람이 갈린 #9(0.90~0.93)의 점수가 높아, #8을 통과시키는 값은 반드시 #7·#9도
> 통과시킨다. 서가 하나만 놓고 본 점수는 082의 정오와 상관이 약하다.

### 튜닝하는 순서

```
① 프롬프트를 고친다     prompts/systemprompt_shelf_fit.txt → 점수 분포가 움직임. 12건 재실행 필요
② 축·평균 정의를 고친다  운영 프롬프트 + schema 설명  → 점수 분포가 통째로 움직임. 12건 재실행 필요
③ 서가 표본을 바꾼다     config.SHELF_SAMPLE(40권)    → 점수의 근거가 바뀜. 12건 재실행 필요
                        config.MAX_UNION_CANDIDATES(3위)
④ 자르는 선을 옮긴다     config.THRESHOLD_2 · GAP_MIN  → 재실행 불필요. 저장된 .json만으로 쓸어볼 수 있음
```

**④를 마지막에 하세요.** ①②③을 고치면 점수 분포가 움직여서 임계값을 어차피 다시 찾아야 합니다.
값은 환경변수로도 바뀝니다:

```bash
LIBCOPILOT_THRESHOLD_2=0.75 python run.py mybook.json
```

## 프롬프트는 파일에 있습니다 — `prompts/`

시스템 프롬프트를 코드 밖으로 뺐습니다. **고치려고 파이썬 파일을 열 필요가 없습니다.**

```
prompts/systemprompt_shelf_fit.txt  독립 fit — 책 1권 × 서가 1곳. 후보마다 같은 지문을 다시 쓴다
prompts/systemprompt_keyword.txt    책 정보만 보고 검색어를 만드는 호출
```

지문이 **둘뿐**입니다. fit 지문 한 줄을 고치면 모든 후보의 점수가 같은 방식으로 움직입니다 —
그게 이 구조의 요점입니다(예전엔 1차·2차 지문이 한 쌍이라 한쪽만 고치면 앞뒤가 어긋났습니다).
**파일명은 ASCII로 둡니다** — 한글 파일명은 OS마다 정규화가 갈려 클론했을 때 "파일 없음"이 납니다.

비교실험에 쓴 다섯 버전은 `../experiment/prompts/`에 보관합니다. 실험기는 환경변수로
그중 하나를 운영 파이프라인에 연결합니다:

```bash
cd ../experiment
LIBCOPILOT_PROMPT_SYSTEMPROMPT_SHELF_FIT=prompts/exp_shelf_fit_two_axis.txt \
  python evaluate.py --label=two_axis
```

어떤 파일로 돌렸는지와 지문 해시가 회차 json의 `setup`에 남으므로, 나중에 그 회차를 재현할 수 있습니다.

운영 `systemprompt_shelf_fit.txt`는 두 축과 평균 방식을 본문에서 직접 정의합니다.
`{SHELF_FIT_RUBRIC}`은 비교실험의 기준선 파일에서만 사용하는 호환용 자리입니다.

|---|---|---|
| **`run.py`** | 책 한 권을 분류하고 결과·근거를 보여준다 | 터미널 |
| **`app.py`** | 사서가 쓰는 데모 화면. 결과 + 근거 + 확정/변경 | `runs/decisions_*.jsonl` |

두 파일 모두 같은 파이프라인(`pipeline.classify_book`)을 부릅니다. `real/` 내부 파일만으로
직접 입력 도서를 처리하며, `experiment/`를 import하거나 골든 정답을 읽지 않습니다.

평가 CLI와 프롬프트 작업창은 `../experiment/`에 있습니다.

## 평가 결과 읽는 법

`cd ../experiment && python evaluate.py`를 돌리면 `experiment/output/`에 회차별 결과가
쌓입니다(덮어쓰지 않습니다).

```
output/<회차>_summary.md     사람이 읽는 비교 요약
output/<회차>.json           케이스별 상세·프롬프트 trace
```

**채점은 책의 종류에 따라 두 갈래다:**

| 유형 | 무엇으로 채점하나 |
|---|---|
| **정답이 하나였던 책** (작성자 == 교열) | 1순위가 그 번호인가 |
| **사람도 갈렸던 책** (작성자 != 교열) | ① 경합한 두 번호를 후보에 다 담았나 ② 사서 확인이 필요하다고 표시했나 |

후자는 *맞히는* 게 아니라 **판단을 사람에게 제대로 넘기는 것**이 성공이다.

> ⚠️ **LLM 판단이라 실행할 때마다 결과가 흔들린다.** 단일 회차 숫자로 판단하지 말고, 같은 조건으로 2~3회 돌려 어떤 케이스가 고정이고 어떤 게 흔들리는지 보는 것이 맞다. 실제로 2026-08-05에 같은 조건 두 회차가 10/12와 9/12로 갈렸고 「부린 왕자」는 정답↔오답이 뒤집혔다.
